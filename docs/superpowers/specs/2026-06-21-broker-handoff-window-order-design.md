# Исправление broker-handoff и порядка окон

## Цель

Устранить повторный запуск разрешённого приложения, разрешить его штатное сворачивание и не позволять полноэкранной оболочке киоска оставаться поверх видимого разрешённого окна. Интерфейс и модель безопасности не изменяются.

## Корневые причины

1. Современный Блокнот Windows запускается через промежуточный `System32\\notepad.exe`, а реальный процесс находится в `WindowsApps` и не всегда является потомком исходного PID. Надзор не распознаёт передачу запуска и исчерпывает пять разрешённых попыток перезапуска.
2. Начальная активация считается завершённой только при успешном `SetForegroundWindow`. Если Windows отклоняет активацию, киоск повторяет восстановление каждые 250 мс и не даёт окну остаться свёрнутым.
3. Полноэкранная оболочка Tk получает foreground при клике и остаётся поверх разрешённого приложения, потому что после первоначального запуска повторное поднятие приложения не выполняется.

## Решение

### Обнаружение переданного процесса

Перед каждым запуском `ProcessRuntime` сохраняет снимок PID процессов с тем же именем файла, что у разрешённого EXE. Если исходный PID быстро завершился, поиск handoff сначала проверяет его потомков, затем ищет новые PID с тем же именем, отсутствовавшие в снимке. Найденный процесс принимается под надзор с его фактическим путём. Существовавшие до запуска процессы не принимаются как новый handoff, поэтому посторонний одноимённый процесс не маскирует неудачный запуск.

Один запуск имеет один снимок. Пока действует окно handoff, новые экземпляры не создаются. После принятия фактического процесса снимок удаляется. При остановке надзора временное состояние также очищается.

### Начальная активация и сворачивание

Начальная активация ожидает появления видимого окна. После первой попытки поднять найденное окно ожидание завершается, даже если `SetForegroundWindow` вернул отказ, но окно существует. Дальнейшие тики только наблюдают состояние и не восстанавливают свёрнутое окно. Разворачивание выполняется исключительно кнопкой `Развернуть`.

### Порядок окон

Оболочка сообщает сессии о клике по canvas после обработки действия кнопки. В состоянии `OPERATOR` сессия просит `ApplicationRuntime` поднять разрешённое окно, только если оно уже видимо. Свёрнутое окно не восстанавливается. В состояниях `ADMIN_DIALOG` и `ADMIN_SESSION` поднятие подавляется, поэтому окно авторизации и административные элементы остаются доступными.

## Совместимость

Одинаковая логика реализуется в modern и legacy ветках. Используются доступные в Windows XP/Server 2003 Toolhelp и Win32 window API; новые обязательные Windows API не добавляются.

## Ошибки и журнал

Ошибки снимка процессов не завершают киоск: handoff продолжает ожидание до штатного таймаута. Пароли и клавиатурный ввод не журналируются. Надзор не завершает чужие процессы и не выполняет массовое завершение.

## Проверка

Регрессионные тесты должны доказать:

- broker-процесс вне дерева исходного PID принимается без второго запуска;
- существовавший до запуска одноимённый процесс не принимается как новый handoff;
- отказ `SetForegroundWindow` не вызывает последующее автоматическое разворачивание;
- клик по оболочке поднимает видимое приложение, но не разворачивает свёрнутое;
- при открытом диалоге администратора разрешённое приложение не поднимается;
- закрытое приложение перезапускается ровно один раз после задержки;
- все modern и legacy тесты, сборки и безопасные smoke-проверки проходят.
